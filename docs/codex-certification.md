# Codex certification

**Status: NOT CERTIFIED.** Codex rule export is experimental and this file says exactly
how far the evidence goes. It exists because a green unit suite proves this repository's
*model* of Codex and nothing about Codex.

Read this before claiming the product "works on both agents". The feature matrix in
`README.md` is the short version; this is the evidence behind it.

## Supported version window

| Field | Value |
|---|---|
| Exercised | `codex-cli` 0.145.0 (2026-09-24, Windows), 0.154.0 (2026-09-24 audit, Windows) |
| Declared window | none yet |
| Rule syntax | `prefix_rule`, generated by `renderCodexRules` |
| Validator | `codex execpolicy check --rules <file> -- <command>` |

Two versions on one platform is a **baseline, not a guarantee**. Nothing pins a window,
and nothing fails when Codex moves outside it. Until that exists, treat every claim below
as scoped to those two versions on Windows.

## What is actually proven

- The generated rules file parses: `codex execpolicy check` accepts it and returns a
  decision. This runs on every write and **fails closed**, so an unvalidated rules file is
  never written. No reachable `codex` binary means no validation and no write.
- The exporter refuses the shapes it says it refuses. `test/policy-exporters.test.js`
  covers the risk classifications, the wrapper rejections and the auto-safe closure rules.
- A rules file is produced at `~/.codex/rules/permission-wildcarding.rules` on this box
  (20,234 bytes as of 2026-09-24) and Codex loads that directory.

## What is NOT proven, and why each matters

**The validator checks one file; Codex evaluates several.** `defaultCodexValidator`
passes a single `--rules` path. `--rules` is repeatable, and Codex resolves a conflict
between visible rule files in favour of the **more restrictive** decision. So a rules file
that validates in isolation can behave differently in situ, and "Why did this prompt?"
can name the wrong cause.

**The managed-requirements parser is approximate.** `enterprisePrefixRules` collects
quoted strings from every pattern position and `enterpriseDecisionFor` compares them all
with `argv[0]`. Root-position `any_of` happens to work. Ordered multi-token patterns and
alternatives in later positions do not, and there is no explicit degraded result for a
shape the parser does not understand.

**Per-rule behaviour is untested against a real binary.** No test proves, for an emitted
rule, an exact positive, a near miss, a non-member of an emitted union, and an inverted
`match`/`not_match`. Nor that a rejected check leaves the deployed file byte-identical
with no recorded application.

**History storage is changing under the reader.** The reader is hard-coded to
`~/.codex/sessions`. Measured on this box 2026-09-24, Codex 0.145.0 writes the rollout
JSONL files the reader consumes **and** maintains a parallel
`~/.codex/thread_history_1.sqlite` (567 items across 20 turns, with a 52-row
`thread_history_projection_state` matching the 52 rollout files) plus a
`session_index.jsonl`. There is also an empty `rollout-migrations/` directory. So the
reader is correct today and has no detector for the day it stops being correct: a
migrated backend would report as a clean scan of a stale directory.

**Workspace scope is withdrawn rather than certified.** Three different trust notions were
in play: VS Code's `workspace.isTrusted`, the CLI's unguarded `--codex-scope workspace`,
and Codex's own project-trust decision, which is not the same as either. Rather than ship
a capability whose trust model could not be stated, workspace scope was removed. User
scope only.

**No real-app proof.** Nothing yet shows, in a fresh Codex session, one generated rule
suppressing the intended prompt while a neighbouring command still prompts, nor that the
generated `AGENTS.md` guidance and memory gates were actually *loaded* rather than merely
written to disk.

## CI

Codex contract tests **cannot run on GitHub's runners**: there is no `codex` binary there
and no authentication for one. They run locally and their evidence lands in this file. Any
CI job that claims to exercise Codex must say on every run that it skipped, never pass
silently, because a check that quietly does nothing is worse than an absent one.

## Account identity is deliberately not read

Codex's policy cache is checked for expiry only. Learning which account is signed in means
opening `~/.codex/auth.json`, which holds live OAuth tokens and an API key, and no feature
here is worth teaching this tool to read that file. This is a decision, not an omission;
see `docs/engineering-record.md`.

## Re-run this when

The supported Codex version window moves, the rule syntax changes, or the session-history
storage changes. Each of those invalidates the evidence above rather than merely ageing it.
